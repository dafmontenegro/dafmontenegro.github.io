A **retrieval-augmented generation** system over the official PostgreSQL documentation, built to test one claim: **the structure of the source HTML decides whether retrieval works, long before the embedding model gets a say.**

[**Repository**](https://github.com/dafmontenegro/postgres-docs-rag) | [**Webpage**](https://montenegrodanielfelipe.com/projects/postgresql-docs-rag/)

It indexes four chapters — Indexes (11), Full Text Search (12), Routine Database Maintenance (24) and Backup and Restore (25) — and answers questions with a citation to the exact section the answer came from, or declines to answer.

This write-up is about the three things that actually decided whether it worked, and one of them is a mistake I made and had to measure my way out of.

## The bug that produced nothing and said nothing

PostgreSQL's documentation is generated by DocBook, which wraps every section like this:

```html
<div class="sect2" id="INDEXES-TYPES-BTREE">
  <div class="titlepage"><div><div>
    <h3 class="title">11.2.1. B-Tree</h3>
  </div></div></div>
  <p>…the actual content…</p>
</div>
```

My first parser found the heading element and walked up to its parent to get the section's container. That parent is the `titlepage` wrapper — three nested anonymous `div`s holding the heading and nothing else.

The scraper did not crash. It returned a chunk for every section, exactly as many as expected, and each one was empty or nearly so. Ingest embedded them. Retrieval ranked them. The system answered questions, badly, and every component reported success.

The fix is to find the `sect1`/`sect2`/`sect3` container by class or anchor id, then walk its children skipping two things: the `titlepage` wrapper, and any nested `sectN` div, because those are chunks of their own.

The reason I lead with this: **no embedding model can rescue a chunk with no content in it.** The failure happened before a single vector was computed, in a layer most RAG write-ups skip past in one sentence about "scraping the docs". That layer is where the quality was decided.

It also argues against reaching for a generic scraper. Everything worth retrieving here *is* structure — the operator table in 11.2.1, the `CREATE INDEX ... USING HASH` syntax, the caution box about transaction ID wraparound. A parser that strips tags returns plain text and throws away the answer. So this one keeps `<pre>` as fenced code, `<table>` as a Markdown table, and note/tip/caution boxes as labelled blockquotes. Off-the-shelf tools that hand back Markdown without the raw HTML make this impossible to debug, because inspecting the cached HTML is exactly how I found the `titlepage` problem.

## The table of contents already knows where the chunks are

The usual default is to split text every N tokens with some overlap. On this corpus that cuts a code block in half, separates a table from the paragraph explaining it, or glues the end of one topic to the start of an unrelated one.

But this documentation is already divided — by its authors, into the units readers actually ask questions at. "11.2.1 B-Tree" is one idea. "24.1.2 Recovering Disk Space" is one idea. So the table of contents defines the boundaries: **one section or subsection, one chunk.** 74 chunks across four chapters, 37,708 words.

The cover image above is those 74 chunks: bar width is word count, indentation is depth in the table of contents.

And it shows the cost of the decision honestly, because sections are not uniform:

| | words |
|---|---|
| Shortest chunk — 25.3.7, "Tips and Examples" | 9 |
| Median chunk | 465 |
| Longest chunk — 24.1.5, "Preventing Transaction ID Wraparound Failures" | 2,242 |
| Chunks over 800 words | 11 of 74 |

That is a 250-fold range, and a fixed-size splitter would not have it. I accept it here because at this scale all 74 chunks would fit in a single prompt if you retrieved every one of them, so an oversized chunk costs context, not correctness. At a larger scale I would split the 11 long sections into paragraphs while keeping the section as their parent, so a hit on a paragraph could still cite its section.

This generalises to documentation with real section structure — technical manuals, API references, legal documents. It does not generalise to prose without headings, where a fixed-size splitter with overlap remains the better default. Structural chunking is not universally better; it is better when the document has structure worth respecting.

## Saying "I don't know", and getting it wrong first

A retrieval system that always answers is worse than useless on a bounded corpus, because its confident answer to an out-of-scope question is indistinguishable from its correct one. So: if the closest chunk is farther than a cosine-distance threshold, the system declines.

I first set that threshold to **0.58**. The reasoning looked sound — I checked a handful of questions about things these chapters plainly don't cover (client authentication, streaming replication, triggers), saw them land at 0.62 and above, saw real questions land below 0.47, and picked a number in between.

The questions I used to check were too easy. They were about *obviously* different topics, so they were far away in every sense. The hard case is a question about a real PostgreSQL feature documented in a neighbouring chapter, phrased in the vocabulary of the chapters I did index — close enough to look like a hit.

So I wrote ten of those and measured. Two broke it:

| Question | Distance | What it retrieved | In corpus? |
|---|---|---|---|
| "Can I use `pg_upgrade` to migrate my cluster to a new major version?" | 0.520 | §25.3.5, recovering from an archive backup | No — Ch. 19 |
| "How do I benchmark index performance with `pgbench`?" | 0.514 | §11.12, examining index usage | No — client apps |

Both sat under 0.58. Both would have been answered, from sections that cannot answer them, with a citation attached to lend the whole thing credibility.

With those questions in the set, the picture is measurable:

| | closest-chunk distance |
|---|---|
| 12 answerable questions | 0.204 – **0.431** |
| 10 out-of-corpus questions | **0.514** – 0.955 |

The groups do separate — but the gap is 0.431 to 0.514, a width of 0.083, and **0.58 was sitting inside the second group**, not between them. The threshold is now 0.47, the midpoint. At that value nothing answerable is rejected and nothing out-of-corpus is accepted, on this set.

I want to be precise about what that last clause is worth, because it is the kind of sentence that sounds like a result and isn't: **the threshold is calibrated on the same questions it is then scored against.** A number fitted to its own test set will always look perfect. The honest claim is narrower — it no longer fails the two specific cases that defeated it, and I know the shape of the questions that find this class of bug.

### What a threshold cannot fix

There is a failure here that no choice of number addresses. Ask: *"How does the BRIN index store its summary tuples internally?"* That retrieves §11.2.6, "BRIN", at distance 0.350 — far inside the accept region, and the retrieval is not wrong. BRIN is genuinely in the corpus. But the *internals* the question asks about are in Chapter 64, and §11.2.6 is an overview. The question is finer-grained than the chunk.

A distance threshold measures whether a question *resembles* the corpus. What you want to know is whether the retrieved text *contains the answer*. Those two come apart exactly here, and the gap is not a tuning problem. The real defence lives one layer up: the generation prompt instructs the model to answer only from the provided excerpts and to say plainly when they are insufficient. The threshold is a cheap first filter that catches the easy half.

## What it costs and what it's made of

Embeddings are `all-MiniLM-L6-v2` running locally — 384 dimensions, no API key, a few seconds for the whole corpus on an M1. The vector store is ChromaDB, local and persistent; at 74 chunks the performance question does not arise, and in production I would move to `pgvector` if PostgreSQL were already in the stack, which costs one fewer system to operate.

Generation is optional, and the system works without it: with no API key it returns the most relevant section with full citations, which answers the question and cites the source — it simply doesn't write prose around it. With a key it uses Gemini Flash Lite's free tier, or Claude Haiku 4.5.

At Haiku 4.5's published rates — $1.00 per million input tokens, $5.00 per million output — a query sends roughly 1.5k tokens of context and returns about 300, so **$0.003 per query**: $0.0015 of input plus $0.0015 of output. At 10,000 queries a day that is about **$30/day**, 15M input tokens and 3M output. Retrieval itself is free, since the embeddings run on the machine.

## What I'd fix next

**Re-ranking, first.** For two questions in the set the expected section arrives at rank 3, not rank 1 — a question about what a `tsvector` represents ranks "Parsing Documents" above the section that defines basic text matching. Both count as hits under a top-3 metric and both would fail at top-1. A cross-encoder over the retrieved four is the standard fix, and the metric I chose is currently hiding the problem.

**Then an evaluation set I didn't write.** All 22 questions are mine, written with the corpus open. That makes the evaluation a smoke test — proof the pipeline does what I think it does end to end — and not a benchmark. The adversarial questions did earn their place by catching the threshold bug, which is the argument for writing them; but a set written by the author of the retriever cannot measure how the system behaves on questions it was never shaped against, and a perfect score on it should be discounted accordingly.

**And change detection.** The corpus is a snapshot taken on 7 August 2026. Re-scraping it on 3 October returned one changed section: in §24.1.5, PostgreSQL had reworded an error message and replaced a reference to `pg_stat_replication` with `pg_replication_slots`. Today the scraper refetches everything and the index is rebuilt whole. For documentation that changed weekly, I would hash each page and reindex only what moved.
